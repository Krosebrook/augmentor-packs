# Reviewing AI-Generated Code

Rule: **don't ship code you can't explain.** AI code is often plausible, confident, and subtly wrong.

## Review pass (in this order)
1. **Intent:** Restate what the code is supposed to do. Ask the user for the original request if missing. Does the code do *that*, or something adjacent?
2. **Hallucinated or outdated APIs:** Verify every import, function, method, flag, and config key exists in the installed version. Check lockfiles/`package.json`/`requirements.txt` and docs. Flag packages that don't exist or look like typosquats — never install an unfamiliar package without checking its registry page, maintainers, and download history.
3. **Correctness:** edge cases (empty, null, large, unicode, concurrency), off-by-one, error paths that swallow exceptions, silent fallbacks that hide failures, time zones.
4. **Security:** injection (SQL, shell, path traversal), secrets in code, disabled TLS verification, overly broad permissions, unsafe deserialization, `eval`, missing authz checks, user input reaching an LLM prompt or a shell.
5. **Tests:** Do tests exist and actually assert behavior (not just that code runs)? AI-written tests often mirror the implementation's bugs. Write at least one test from the spec, not the code.
6. **Maintainability:** dead code, duplicated logic, unnecessary abstractions, inconsistent style with the rest of the repo, comments that describe what the code doesn't do.

## Comprehension check (the augmentor part)
Before approving, ask the user 2–3 questions about the code: "What happens if X is empty?", "Why is this lock needed?" If they can't answer, walk through it together until they can.

## Output
Verdict (**Merge** / **Merge after fixes** / **Rewrite**), then findings as `file:line | severity | issue | why | suggested fix`, then the comprehension questions. Run linters, type checkers, and tests if tools are available and report the actual output.
